Folio plugins expose a typed lifecycle API integrated with Folio's production
build command. Development/watch lifecycle behavior remains a separate
milestone.

## Register a plugin

Create configured plugins with a factory, then register the returned plugin in
`docs.config.ts`:

```ts
import { createFolioPlugin } from "@nikala-ui/folio";

const reportPlugin = createFolioPlugin(
  (options: { file: string }) => ({
    name: "build-report",
    generate(context) {
      context.logger.info(`Would write ${options.file} for ${context.pages.length} pages`);
    },
  }),
  { file: "build-report.json" },
);

export default { plugins: [reportPlugin] };
```

`defineFolioPlugin(plugin)` is available when a plugin does not need options.
Both helpers validate the plugin registration and require a non-empty unique
name in a `DocsConfig.plugins` array. Hook fields, when present, must be
functions. Invalid registrations fail configuration loading with an actionable
error.

## Public contract

`FolioPlugin` currently exposes these optional hooks:

- `configResolved(context)`
- `buildStart(context)`
- `pageCollected(page, context)`
- `pageTransformed(page, context)`
- `generate(context)`
- `buildEnd(result, context)`

The context and result types are exported from `@nikala-ui/folio`. The
production build invokes these hooks through the lifecycle manager. The
`generate` context exposes the absolute production `outputDir` and the final
immutable `pages` catalog; `outputDir` is omitted for sessions that do not
produce production artifacts, such as development sessions.

## Lifecycle order

An integrating build tool must invoke hooks in this order:

```text
load config
  -> configResolved
  -> buildStart
  -> content scan
  -> pageCollected (for each page)
  -> pageTransformed (for each page and plugin)
  -> route tree, sidebar, and pagination
  -> MDX compilation
  -> artifact generation
  -> generate
  -> buildEnd
```

Hooks run sequentially in registration order. A hook failure stops the current
operation and is reported as `FolioPluginHookError`, preserving the original
error in `cause` and adding the plugin name, hook, mode, and page location when
available.

The hook responsibilities and contracts are:

| Hook | Input | Contract |
| --- | --- | --- |
| `configResolved` | build context | Observe the final resolved configuration before scanning. |
| `buildStart` | build context | Prepare plugin state before content discovery. |
| `pageCollected` | page and context | Observe one scanned `PageData` snapshot. |
| `pageTransformed` | page and context | Return transformed `PageData` while preserving `slug` and `url`. |
| `generate` | build context | Run after artifact generation; production contexts include `outputDir` and the final page catalog. |
| `buildEnd` | build result and context | Observe the final immutable result, including failed results. |

If a hook fails, later plugins and later hooks in the current operation are not
called. The integrating tool owns the final process-level failure handling, but
the lifecycle manager always wraps an unhandled hook failure and retains its
original cause. `buildEnd` receives `success: false` when the integrating tool
reports a failed build; it does not convert a failed build into a successful
one.

`pageTransformed` may update a page's metadata, including its title,
description, order, badge, icon, table of contents, and frontmatter-derived
values. It must preserve the page route identity (`slug` and `url`). The first
contract does not allow plugins to add routes or replace MDX source content. A
transformation is applied before route tree, sidebar, and pagination generation
so those structures consume the transformed page metadata. Source-content
transformation is intentionally excluded from this contract and requires a
future, separately specified API.

Hook inputs are immutable snapshots, so plugins cannot mutate Folio's
configuration or collected page data. This includes nested objects, arrays,
maps, sets, dates, regular expressions, and supported provider instances. The
original config and page objects remain unchanged.

Plugin packages should keep feature-specific behavior (such as i18n, API
documentation, or workspace discovery) outside the core package. Development
and watch-mode lifecycle integration remains a separate milestone.
